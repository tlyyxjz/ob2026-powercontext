# 一页技术说明

## 1. 要解决的问题

AI 开发助手改代码时，缺的不是生成能力，而是**依据**：这条改动该遵守哪条规格、该动哪个符号、
改完该跑哪些测试、上次做到哪了。资料散落在 Markdown、源码和测试里，规格还会变。

本模块把这件事拆成四步并各自落到一项技术上：

```
任务描述 ──► [seekdb 检索] ──► 规格条目 + 代码符号 + 测试用例
                                   │
                                   ├──► 提示词 ──► MiniMax ──► 代码修改 ──► 应用 & 测试
                                   │
                                   └──► PowerContext 保存「进展 / 验证结果」──► 下次运行读回
```

## 2. 模块结构

| 文件 | 职责 | 关键实现 |
|---|---|---|
| `importer.py` | 把规格、代码、测试解析成结构化记录 | 规格按 `## R<n> <标题>` 切条；代码用标准库 `ast` 取类/函数及其行区间、签名、docstring；测试用 `ast` 取 `test_*` 并从 docstring 识别所覆盖的规格条目 |
| `store.py` | 落库、检索、查询留痕 | seekdb 五张表：`spec_items` / `code_symbols` / `test_cases` / `import_runs` / `query_log`；每次检索都把 SQL、参数、命中行数写入 `query_log` |
| `agent.py` | 组装提示词、调用模型、安全落地 | 只让模型输出**单个函数的完整源码**（不让它出 diff）；用 `ast` 定位原函数行区间做替换，替换前后各做一次语法校验，任一失败则不落盘 |
| `state.py` | 任务状态持久化 | PowerContext 一个任务一个 Scope，每次保存追加一条 `task-state` 条目，读取取 `created_in_revision` 最大者 |
| `minimax_client.py` | MiniMax 接入 | 只用公开 HTTP API；记录耗时、token、原始输出，不记录思维链 |
| `cli.py` | 统一入口 | `init / import / context / state / propose / apply / verify` |

## 3. 上下文是怎么选出来的

**流程**：任务文本 → 关键词抽取 → 三张表分别检索 → 打分排序 → 组装。

**关键词抽取**（`store.extract_keywords`）：英文按下划线/驼峰标识符原样保留并小写化；
中文按**二元组**切分（无分词器依赖时的稳定做法）；两侧都去掉停用词。

**检索**：对每张表做 `LIKE '%kw%'` 的 OR 组合查询，由数据库返回候选集，
再在进程内按命中位置打分：

| 表 | 打分维度（权重从高到低） |
|---|---|
| `spec_items` | 标题命中数 > 正文命中数 |
| `code_symbols` | 符号名命中数 > docstring 命中数 > 路径命中数 |
| `test_cases` | 测试名命中数 > `covers` 命中数 > docstring 命中数 |

**为什么不用向量检索**：本任务的检索目标是**标识符级的精确匹配**（`filter_tasks`、`SPEC-001#R2`），
关键词匹配在这种场景下的可解释性更好，且命中来源可以直接引用给评审核对。
代价是同义词召回弱——这条与其它限制一并列在 `README.md` 第 8 节。

**来源真实性**：`context` 命令在输出末尾附带 `missing_sources`，逐个校验引用路径是否存在，
非空即返回非 0 退出码。这样「输出里的来源必须真实存在」变成了一条**可自动检查**的约束，
而不是靠人工核对。

## 4. 三项技术各承担什么

| 技术 | 在本任务中承担的作用 | 可核对的痕迹 |
|---|---|---|
| **MiniMax**（`MiniMax-M3.1-Flash`） | 本次任务的**代码生成**：接收规格条目 + 目标函数原文 + 测试要求，输出修改后的 `filter_tasks` | `records/minimax_devlog.md`（时间/模型/耗时/token/上下文摘要）、`T-001.minimax_raw.txt`（原始响应）、`T-001.applied.diff`（与实际代码差异一致） |
| **seekdb**（`seekdb-v1.4.0.0`） | **工程资料的存储与检索**：规格条目、代码符号、测试用例三张表，检索结果直接构成上下文的三个组成部分 | `records` 中 `query_log` 表的 SQL 与命中行数；`import` 命令输出的 `imported.spec_items=6 / code_symbols=10 / test_cases=14` |
| **PowerContext** | **任务状态持久化与复用**：保存「当前规格版本 + 已完成/待办 + 每次测试的退出码」，模块重启后读回并注入下一次上下文输出 | `records/powercontext_state.log`（每次 save/load 的 revision）、`context` 输出中的 `state` 字段、`state show` 在**新进程**中读回 `verifications=[1, 0]` |

三者都不是「装了就算」：

- seekdb 的表如果没数据，`context` 输出的 `specs/symbols/tests` 会全空，`propose` 直接拒绝生成；
- PowerContext 的状态如果读不到，`context` 的 `state` 字段就是 `null`，验收第⑤项会失败；
- MiniMax 的输出如果没被应用，`verify` 的退出码仍然是 1。

## 5. 关键设计取舍

**（1）让模型输出整函数，而不是 diff。**
diff 的行号和上下文极易错位，一旦错位就无法自动应用，且难以在事后判断是「模型写错了」还是
「应用错了」。整函数替换可以用 `ast` 精确定位行区间，替换后立刻 `ast.parse` 校验，
失败则不动原文件——把「模型不可靠」的风险挡在落盘之前。

**（2）规格更新用整体替换，不是增量合并。**
`store.replace_corpus` 在一个事务里清空三张资料表再写入。这样「规格从 v1 更新到 v2」之后，
库里不会残留 v1 的条目，上下文输出也就不会混进旧约束。代价是每次导入都是全量，数据量大时
需要改成按文档差异更新。

**（3）状态用追加而非覆盖。**
每次保存都追加一条新条目，`_revision` 递增。这样任务进展本身成为可追溯的序列
（本次实测：`revision=2`，`verifications=[1, 0]` 完整记录了「先失败后通过」）。
读取时取 `created_in_revision` 最大的那条——注意 `MemoryEntryVersion.version` 是
**条目自身**的版本号（首次写入均为 1），不能用来跨条目排序。

**（4）验证样例自带「改前」证据。**
`samples/task-001/service.before.py` 是修改前的源码快照，`context_v1.json` 是 v1 规格下的上下文。
评审不需要相信任何口头说明，按第 4 节的重置步骤就能把工程打回原状，自己跑一遍「红 → 绿」。
