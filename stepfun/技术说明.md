# 技术说明 · seekdb 边缘知识库

交付物对应 OceanBase AI 生态赛道 **阶跃星辰题（20 分）**。
本文所有数字都标了口径与来源；没有估算值，也没有把「预期」写成「实测」。

---

## 一、方案一句话

**把文档向量化搬进浏览器，把两路结果的融合留给 seekdb，中间层只搬数据。**

三个约束决定了这个形状：

1. 文档不能离开本机 ⇒ embedding 的调用点必须在浏览器里；
2. 端侧没有服务端算力 ⇒ 模型要量化后随包分发；
3. 单一通道都不够用（详见 §5.2）⇒ 必须向量 + 全文，且融合不能放在应用层。

---

## 二、三层分工

```
浏览器（用户设备）                    Node 服务（本机）              seekdb（本机）
─────────────────────              ────────────────────         ──────────────────
① 加载 INT8 权重（仅从 /models/）                               
② 文档切块 → 逐条算 384 维向量                                  
③ 把 [文本, 向量] 一起 POST  ───→  ④ add() 落库                 
                                    ⑤ refresh_index()  ────────→ 建 HNSW 索引
⑥ 查询文本 → 算 384 维向量                                      
⑦ 把 [原句, 向量] 一起 POST  ───→  ⑧ 调一次 hybridSearch() ───→ 全文通道 + 向量通道
                                                                    RRF 融合（库内）
⑩ 渲染排序结果 + 分数       ←───   ⑨ 原样返回 ids / 分数         
```

**边界用代码保证，不靠文档约定：**

- `server/seekdb.mjs` 里**没有任何推理调用**，也没有任何「分别取两路再拼」的方法。
  想拼也拼不出来 —— 混合检索只暴露了 `hybridSearch()` 一个入口。
- `web/worker-embed.js` 里 `env.allowRemoteModels = false`，
  模型字节只能来自本机 `/models/`，运行期没有可用的远端推理路径。

## 三、模型：来源、量化方式、体积、质量

### 3.1 来源

| 项 | 值 |
|---|---|
| 模型 | `Xenova/all-MiniLM-L6-v2`（Transformers.js 官方导出的 ONNX 版本） |
| 运行时 | `@huggingface/transformers` 3.8.1 + ONNX Runtime Web |
| 获取方式 | `scripts/fetch-model.mjs` 从 ModelScope 镜像拉取 |
| 为什么用镜像 | HuggingFace 直连在本机 `fetch failed`；ModelScope 上是同一份布局、同一份字节 |

拉到本机后由本服务以静态文件提供，**运行期模型字节全部来自 localhost**。
`fetch-model.mjs` 打印的是**实际落盘字节数**，不是调用方声明的值：

```
config.json                             650 B
tokenizer.json                       711,661 B
tokenizer_config.json                    366 B
onnx/model.onnx                   90,387,606 B   ← FP32
onnx/model_quantized.onnx         22,972,370 B   ← INT8
```

### 3.2 量化方式

选 **INT8**（题面允许 INT8 或 FP16）。用的是上游已经量化好的 `model_quantized.onnx`，
不是我们在本地重做的量化 —— 这样评审可复现，也避免引入一套自己的量化脚本误差。

Transformers.js 里通过 `dtype: "q8"` 选中这个权重文件；
`fp32` 会用 `model.onnx`（只在对照实验里用）。

### 3.3 体积对比

| 权重 | 实测字节 | 相对 |
|---|---|---|
| FP32 `model.onnx` | 90,387,606 B | 1.000× |
| INT8 `model_quantized.onnx` | 22,972,370 B | **0.254×（3.935× 更小）** |

口径：`fs.statSync` 读盘上大小，不是「参数量 × 位宽」估的。
（这一条写在语料 s24 里，也是踩过的坑：估算值和实际值能差几个百分点。）

### 3.4 质量变化

`npm run bench`，12 条人工标注查询 × 24 条文档，纯余弦排序（不经数据库）：

| 指标 | FP32 | INT8 | 变化 |
|---|---|---|---|
| Recall@5 | 0.4167 | 0.3750 | −0.0417 |
| MRR@5 | 0.4194 | 0.4027 | −0.0167 |
| Top5 排序重合度 | — | 0.85 | — |
| Top1 一致 | — | 9/12 | — |
| 向量分量最大绝对偏差 | — | 0.044023 | — |

**怎么读这组数：**

- 掉 4 个百分点的 Recall@5、Top1 有 3/12 换了答案 —— 量化不是无损的，边界样本上会翻。
- 但降幅**远小于**体积的收益（体积降到 1/3.9，召回只掉 1/11），对端侧是划算的。
- **Recall@5 绝对值只有 0.42，不是量化造成的**，而是这个模型本身在中文上的短板：
  all-MiniLM-L6-v2 是纯英文语料训练的。这正好解释了为什么这道题必须做混合检索 ——
  见 §5.2。把 0.42 写成「模型很好」是误导；把它写成量化的问题也是误导。

## 四、后端：WebGPU 优先，WASM 兜底

### 4.1 探测与降级

```js
// 主线程先探一次，把结果告诉 Worker
if (!navigator.gpu) return { ok: false, reason: "navigator.gpu 不存在" };
const adapter = await navigator.gpu.requestAdapter();
if (!adapter) return { ok: false, reason: "requestAdapter() 返回 null" };

// Worker 按 [webgpu, wasm] 顺序尝试，失败就换下一个，并把原因回传
const order = msg.preferWebgpu ? ["webgpu", "wasm"] : ["wasm"];
```

降级不是静默的：界面上 badge 显示「推理后端 **WASM · 已降级**」，
日志里写明 `WebGPU 不可用：requestAdapter() 返回 null（没有可用适配器）`。

**实测两种环境都覆盖到了：**

| 环境 | `navigator.gpu` | `requestAdapter()` | 实际后端 |
|---|---|---|---|
| 无头 Chromium（三种旗标组合） | 存在 | **null** | WASM（降级） |
| 有头 Chromium（AMD RDNA-2 集显） | 存在 | 拿到适配器 | **WebGPU** |

无头下试过 `--enable-unsafe-webgpu`、`--use-angle=swiftshader`、`--use-angle=vulkan` 三种组合，
`requestAdapter()` 全部返回 null ⇒ **降级是环境事实，不是我们人为关掉的**。

### 4.2 实测延迟矩阵

本机 AMD RDNA-2 集显，每组 12 次，**首次**与**稳态中位数**分开报：

| 场景 | 实际后端 | 首次 | 稳态中位 | 折合单条 | 模型加载 |
|---|---|---|---|---|---|
| 单条 · INT8 | webgpu | 506.2 ms | 129.5 ms | 129.5 ms | 1,422.4 ms |
| 单条 · INT8 | wasm | 30.0 ms | **11.0 ms** | 11.0 ms | 329.5 ms |
| 单条 · FP32 | webgpu | 612.2 ms | 28.1 ms | 28.1 ms | 1,873.6 ms |
| 单条 · FP32 | wasm | 154.6 ms | 23.4 ms | 23.4 ms | 1,003.4 ms |
| 批量8 · INT8 | webgpu | 592.0 ms | 182.0 ms | 22.8 ms | 1,046.5 ms |
| 批量8 · INT8 | wasm | 150.4 ms | 72.3 ms | **9.0 ms** | 679.8 ms |

### 4.3 为什么本机 WASM 反而更快 —— 归因，不是猜测

两个单变量对照：

**对照 A（只改精度，同一 WebGPU 会话）**
`webgpu + INT8` 稳态 129.5 ms → `webgpu + FP32` 稳态 28.1 ms（**4.6×**）。
同一个 GPU、同一个会话、同一条文本，只换了权重精度。
⇒ 慢的不是 GPU 算力，是 **INT8 权重在 WebGPU EP 上要额外 dequantize** 这条路径。

**对照 B（只改批量，同一后端同一精度）**
`webgpu + INT8` 单条 129.5 ms → 批量 8 折合单条 22.8 ms（**5.7×**）。
⇒ GPU 的并行度要靠批量才吃得到，单条推理对它最不利。

**这是取舍，不是缺陷声明。** 默认策略仍按题意：**支持 WebGPU 就优先 WebGPU**。
理由：题面要求的就是这个策略；而且换成 FP32 后 GPU 路径并不差（28.1 vs 23.4 ms），
如果后续把权重换成 FP16，GPU 侧大概率还能再快。

> ⛔ **不外推**：以上只覆盖这一台机器、这一个模型、这一版 onnxruntime-web。
> 不能据此说「WebGPU 一定比 WASM 慢」。

## 五、seekdb 侧

### 5.1 索引与集合

`getOrCreateCollection` 不传 schema 时的默认值（实测读回 `/api/status`）：

```json
{ "fulltextIndex": { "analyzer": "ik", "properties": {} },
  "vectorIndex": { "hnsw": { "dimension": 384, "distance": "cosine" } } }
```

中文全文索引用的是 `ik` 分词器 —— 这是默认值，不是我们额外配的。

### 5.2 为什么必须混合：单通道各自缺什么

| 通道 | 强在 | 弱在 | 语料里的实证 |
|---|---|---|---|
| 全文 `$contains` | 专有名词、参数名、错误码这类字面量 | 同义改写完全无能为力 | 查 `ef_construction` 能精确命中 s03 |
| 向量 | 语义相近、用词不同 | 中文上弱（模型只受过英文训练，§3.4） | 查 `怎么让搜索结果更准` 命中 s09 |

两条都需要，缺一条就有一类问题查不到。

### 5.3 全文通道是怎么构造的（这一节是踩坑记录）

**问题**：seekdb 的 `$contains` 是**子串匹配**（等价 `LIKE '%x%'`），不是分词后的 AND。
把整句 `HNSW 的 ef_construction 调大会怎样` 直接丢进去，**全文通道恒空** ——
混合检索静默退化成纯向量，看起来"能跑"，实际上混合没发生。

**做法**：把查询摊成若干可字面命中的检索项，再用 `$or` 组合：

```js
// 英文/数字 token：按词边界切，长度 ≥ 2（参数名、错误码靠它精确命中）
for (const m of text.matchAll(/[A-Za-z][A-Za-z0-9_+\-.]*[A-Za-z0-9]|[A-Za-z]{2,}|\d{2,}/g)) …

// 中文：2-gram 滑窗（无词典也能切，且「召回」能命中「召回率」）
for (const chunk of text.match(/[\u4e00-\u9fff]+/g) ?? [])
  for (let i = 0; i + 2 <= chunk.length; i += 1) …
```

语义上等价「任一词条字面出现即算全文命中」。

**代价（如实写）**：2-gram 的 OR 语义偏松，会有噪音。
实测 `向量索引写入后为什么查不到` 的 #1 是讲余弦距离的那条 —— 它靠「向量」这个词进了全文通道。
正确答案 s11 排 #2（0.0315 vs 0.0320），差距很小但确实被压了一名。
这是朴素 `$contains` 的固有取舍；要根治得让数据库支持分词 AND 或多字段权重，不在本题范围内。

### 5.4 融合确实发生在库内 —— RRF 分数逐点核对

`hybridSearch` 返回的 `distances` 就是融合后的 RRF 分。若融合是客户端拼的，
分数不会严格落在 `Σ 1/(k+rank)` 上。实测 `k=60`（`rankConstant: 60`）：

**单通道命中**（7 个观测点全中）：

| 观测分 | 对应 | 校验 |
|---|---|---|
| 0.0164 | 1/61 | 0.016393 ✅ |
| 0.0161 | 1/62 | 0.016129 ✅ |
| 0.0159 | 1/63 | 0.015873 ✅ |
| 0.0156 | 1/64 | 0.015625 ✅ |
| 0.0154 | 1/65 | 0.015385 ✅ |
| 0.0152 | 1/66 | 0.015152 ✅ |
| 0.0149 | 1/67 | 0.014925 ✅ |

**双通道命中**（两项之和）：

| 观测分 | 对应 | 计算 |
|---|---|---|
| 0.0328 | 1/61 + 1/61 | 0.032787 ✅ |
| 0.0323 | 1/61 + 1/62 | 0.032522 ✅ |
| 0.0320 | 1/62 + 1/63 | 0.032002 ✅ |
| 0.0315 | 1/63 + 1/64 | 0.031498 ✅ |
| 0.0308 | 1/63 + 1/67 | 0.030798 ✅ |

单通道分严格等于 `1/(60+rank)`、双通道分严格等于两项之和 ⇒ **融合在库内完成**，
服务端拿到的已经是排好序的最终结果。界面上「双通道 / 仅向量通道」的标记，
就是按 `1.5/(k+1)` 阈值从分数反推的（**标注：这是反推，不是数据库直接给的字段**）。

### 5.5 刷新语义

写入后**必须显式刷新**，否则向量通道查不到新数据：

| 步骤 | 读数 |
|---|---|
| add 5 条后直接 query | **0 条** |
| 首次 `refresh_index()` | 34,713 ms → `Timeout (ret=-4012)` |
| 重试 | **403 ms 成功** |
| 刷新后再 query | 正常返回 |
| 增量 add 1 条 → refresh | 403 ms |

首次刷新会撞内部超时是个真实坑，所以 `refreshWithRetry` 最多重试 3 次、
每次都把真实耗时回报到界面（「第1次 成功 416 ms」这种）。
在 24 条的小批量下三次测试都是首次即成功（235 – 416 ms），
说明**这个超时和批量/数据量有关，不是每次都会触发** —— 不能写成「必然超时」。

## 七、已知取舍一览

1. **2-gram 全文通道偏松**（§5.3）—— 会引入关键字噪音，但比"全文通道恒空"好得多。
2. **MiniLM 中文弱**（§3.4）—— 模型选型问题，不是实现问题；混合检索就是为它补的。
3. **本机 WASM 快于 WebGPU**（§4.3）—— 已归因到 INT8 在 GPU EP 上的 dequantize；
   策略上仍按题面优先 WebGPU。
4. **首次刷新可能撞 `ret=-4012`**（§5.5）—— 有重试，且真实耗时对用户可见。
5. **`bench.mjs` 跑在 Node 里** —— 它是离线质量评测，不参与应用运行时路径；
   应用里的向量只可能在浏览器算。这一点在脚本顶部注释里也写明了，避免被误读成
   「服务端也能算向量」。
